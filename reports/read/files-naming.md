# Naming generation outputs: files, media, results, artifacts?

Report, 2026-07-05. What do we call the things generations produce — inclusively over images,
video, audio, meshes, splats, and LLM text — and does the name survive a future of
fine-tunes, trained models, vectors, long-term hosting, and remixing?

---

## The key move: it's two concepts, not one

The confusion dissolves once you split **storage** from **provenance**:

1. **`files`** — the storage primitive. Bytes in R2 with a mime type, checksum, size, CDN
   URL. A file doesn't know or care what it means. Everything durable is ultimately a file:
   an input photo, a generated video, a thumbnail, someday LoRA weights, a fine-tune
   checkpoint, an exported embeddings blob, a training dataset archive.
2. **`outputs`** — the job-product record (already `job_outputs` in schema.md): "job X
   produced this, at index 2, of kind video." An output *references* stored bytes; it carries
   the generation provenance (job, index, kind, dimensions).

With that split, every future case has an obvious home:

| Future thing                    | Modeled as                                                       |
| ------------------------------- | ----------------------------------------------------------------- |
| Long-term hosted media          | Files (they already live forever; hosting product = ACLs + serving tiers on files) |
| Remixing outputs into new jobs  | Any file ID is valid in any input slot — output of job A is input of job B, no conversion. This is the workflow foundation |
| Fine-tuned model / LoRA weights | A future first-class resource (`adapters` or `custom_models`) whose *weights* are files. The resource carries semantics (base model, training config, status); the file carries bytes |
| Trained full models             | Same pattern, bigger files. Still not "a file" at the API surface — a model resource that owns files |
| Embeddings / vectors            | If queryable: a vector store, not files. If exportable artifacts: files |
| LLM text results                | Small enough to live inline on the job/output row (`kind = text`); still an output, optionally also persisted as a file when large |

So: **don't** stretch one noun over everything. Files stay dumb; meaning lives on the
referencing resource (output, adapter, dataset).

## The candidate names, judged

| Term          | Verdict                                                                              |
| ------------- | ------------------------------------------------------------------------------------ |
| **files**     | KEEP for the storage primitive. Boring, universal, matches OpenAI/Replicate `/files` precedent for uploads; nothing it can't cover because it promises nothing |
| **outputs**   | KEEP for job products. Says exactly what it is relative to a job; symmetric with "inputs"; already our table name |
| media         | REJECT as the primitive: excludes text and (awkwardly) meshes/splats/weights; fine as an informal word in marketing ("media APIs") |
| results       | REJECT: transient connotation (a "result" feels ephemeral, ours live forever); collides with poll-response phrasing ("the result of the status check") |
| artifacts     | CLOSE SECOND for outputs — precise engineering meaning (thing produced by a process) — but carries CI/build-pipeline flavor, and "job outputs" beats it on plain-English clarity for customers |
| assets        | REJECT: design/DAM-tool flavor, and dangerously overloaded once billing exists ("assets" means money things) |
| generations   | REJECT as the noun for stored things (it names the *event*, not the object; OpenRouter uses it for request accounting). Fine informally |
| creations     | REJECT: Vidu uses it; twee |

## Recommendation (matches current schema, so: no change, one rename to consider)

- `files` (`file_`) = storage primitive, both uploads and — proposal — generated bytes too.
- `job_outputs` (`out_`) = provenance records pointing at stored bytes.
- One refinement worth making when convenient: today `job_outputs` carries its own
  storage_key/cdn_url columns; migrating it to reference a `files` row (outputs become
  pure provenance + FK) unifies storage handling before the hosting/remix products land.
  Cheap now, annoying later.
- Future trained things get their own resources that own files; never "special files."
