# API-specific domains: who does it, and should we?

Report, 2026-07-05. (You asked for `api-domain.rs` — assuming `.md` was intended.)
Question: Fal has `fal.run` — do others use dedicated API domains, and should we?

## The landscape (from memory of public docs; spellings verifiable on each vendor's docs)

### Dedicated short invocation domains (the fal.run pattern)

| Vendor      | Site           | Invocation / workload domain                | Purpose                              |
| ----------- | -------------- | -------------------------------------------- | ------------------------------------ |
| Fal         | fal.ai         | `fal.run`, `queue.fal.run`                    | Model invocation (sync/queue)        |
| Modal       | modal.com      | `*.modal.run`                                 | Deployed function endpoints          |
| Cloudflare  | cloudflare.com | `*.workers.dev`                               | Deployed worker endpoints            |
| Vercel      | vercel.com     | `*.vercel.app`                                | Deployments                          |
| Fly.io      | fly.io         | `*.fly.dev`                                   | Deployed apps                        |
| Deno        | deno.com       | `*.deno.dev`                                  | Deployed apps                        |
| Netlify     | netlify.com    | `*.netlify.app`                               | Deployed sites                       |
| Hugging Face| huggingface.co | `router.huggingface.co`, `*.hf.space`         | Inference-provider routing; Spaces   |

### Separate asset / user-content domains (near-universal at scale)

| Vendor      | Content domain                     | Why a separate domain                        |
| ----------- | ---------------------------------- | -------------------------------------------- |
| Replicate   | `replicate.delivery`               | Generated outputs                             |
| Fal         | `fal.media` / `v3.fal.media`       | Generated outputs                             |
| GitHub      | `githubusercontent.com`            | The canonical example: user content must not share the auth origin |
| Google      | `googleusercontent.com`            | Same                                          |
| Discord     | `cdn.discordapp.com`               | Same                                          |
| Slack       | `files.slack.com`                  | Same                                          |

## Why the split exists (not vanity)

1. **Cookie/session isolation.** Serving user-generated bytes (HTML-adjacent SVGs, videos,
   glTF) from the same origin as your console cookies is an XSS/session-theft footgun.
   `githubusercontent.com` exists because GitHub learned this the hard way.
2. **Workload isolation** (the `.run`/`.dev` pattern): user-triggered compute gets a domain
   whose reputation (spam/abuse/blocklists) can burn without torching the marketing site or
   transactional email domain.
3. **Public Suffix List**: the `*.workers.dev`-style multi-tenant domains are on the PSL so
   one tenant can't set cookies for another. Matters if we ever give accounts subdomains.
4. **Ops freedom**: separate TLS/CDN/WAF policy per domain; apex-short domains also just read
   great in code (`POST https://fal.run/...`).

## Recommendation for us

| Surface               | Domain                              | Notes                                        |
| --------------------- | ----------------------------------- | -------------------------------------------- |
| Marketing + console   | `{name}.ai` (or .com)               | Cookies live ONLY here                        |
| API                   | `api.{name}.ai` at launch           | Boring and correct; optionally add a short vanity apex later (`{name}.run` / `.dev`) as an alias — fal.run proves the ergonomic value |
| Generated media CDN   | **separate registrable domain**, e.g. `{name}media.com` or `{name}.delivery` | Non-negotiable before public launch — user content off the auth origin |
| Docs                  | `docs.{name}.ai`                    | Netlify                                       |

The one hard requirement is the media domain; the vanity API apex is a nice-to-have that can
wait for the product name decision (see `name-ideas.md` — e.g. `relay.run` if Relay wins and
is available).
