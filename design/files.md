## 1. Two concepts, two tables (DECIDED 2026-07-14)

**Sign-off:** _unsigned_

Yes — two tables. The design splits **storage** from **provenance**
(`../reports/read/files-naming.md`):

| Table     | Role                                                                                                                                                                     |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `files`   | The storage primitive: bytes in R2 with mime, size, checksum, CDN URL. A file doesn't know or care what it *means*. Uploads AND generated bytes alike                    |
| `outputs` | The job-product record: "job X produced this, at index 2, of kind video." Pure provenance — it **references** a `files` row rather than carrying its own storage columns |

- Jobs have **zero or more** outputs (a failed job has none; a batch image job has several).
- Everything durable is ultimately a file: an input photo, a generated video, a thumbnail —
  someday LoRA weights, a fine-tune checkpoint, an exported embeddings blob.
- **Remix seam:** any `file_...` ID is valid in any input slot — the output of job A is an
  input of job B with no conversion. This is the workflow foundation.
- **Fine-tunes seam:** a future trained thing (LoRA, fine-tune, full model) is its own
  resource (`custom_models`-style) whose *weights* are files. The resource carries semantics
  (base model, training config, status); the file carries bytes. Never "special files."
- **Text is an output too:** LLM/text products are outputs of `kind = text` — storage
  decision in §3.

Storage details (key, CDN URL, mime, bytes, checksum, class, provider URL) moved to `files`
— the report's refinement, adopted: "outputs become pure provenance + FK; unifies storage
handling before the hosting/remix products land. Cheap now, annoying later."

## 3. Text outputs: inline column, file spillover (DECIDED 2026-07-14)

**Sign-off:** _unsigned_

How the field stores completion text:

| Provider   | Where completion text lives                                                                                                                                      |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenAI     | Their DB, inline on the response/completion object, retrievable by ID (30-day window on Responses); **files only for Batch API** output (JSONL `output_file_id`) |
| Anthropic  | Not stored (stateless Messages); batch results delivered as a results file                                                                                       |
| OpenRouter | **Not stored at all** — `/v1/generation` returns token/cost metadata only                                                                                        |
| Replicate  | Prediction `output` JSON in their DB (text inline); media on their CDN                                                                                           |

Nobody CDN-hosts interactive chat text; files appear only for batch products. Options:

| Option                                     | Verdict                                                                                                                                                                                                  |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Always an R2 file, uniform with media      | Rejected: a CDN URL for a chat reply is user-hostile (extra fetch to read your own completion), and it makes the text opaque to SQL                                                                      |
| Separate `output_texts` table (1:1)        | Rejected: a second table to keep `outputs` skinny is what TOAST already does — Postgres stores large text out-of-line automatically                                                                      |
| **Inline `text_content` + file spillover** | **DECIDED** — inline on the output row up to **1 MB** (the logging cap constant, reused); beyond that, write an R2 file and set `file_id` instead. Matches field practice, keeps the read path one query |

Rules: exactly one of `text_content` / `file_id` is set per text output (the CHECK in §2);
job responses return inline text directly and a CDN URL when spilled. Spillover is expected
to be rare (1 MB ≈ 250k+ tokens of output).

## 4. Thumbnails — DEFERRED (2026-07-14)

**Sign-off:** _unsigned_

No thumbnails table, no thumbnail generation in v1. Decisions taken now so the seam is
clean:

- **A thumbnail is not an output** — `thumbnail` removed from `OutputKind`. It's a *derived
  file*: when built, a thumbnail is a `files` row (`purpose = thumbnail`) plus a
  `derived_from_file_id` FK column on `files` (additive migration, reserved not built).
- **Never gate job success on thumbnails.** `succeeded` means outputs are ingested and
  durable (`jobs.md` §2) — full stop. Thumbnail generation, when it exists, runs
  post-success as an ordinary `queue_tasks` entry (`generate_thumbnails`, keyed by file id);
  a late or failed thumbnail changes nothing about the job.
- **No jobs-table FKs needed** — the queue task and the `derived_from_file_id` chain carry
  everything; consumers find a file's thumbnail via `files WHERE derived_from_file_id = $1`.

## 5. API surface

**Sign-off:** _unsigned_

- `POST /v1/files` — multipart upload → `file_...` usable in any input slot (`api.md` §7).
- Outputs are **embedded** in job responses (`GET /v1/jobs/{id}` returns the outputs array
  with CDN URLs); no standalone `/v1/outputs` listing in v1.
- `succeeded` is set only AFTER outputs' bytes are ingested into our storage (`jobs.md` §2)
  — a `succeeded` job's output URLs are always durable, ours.
